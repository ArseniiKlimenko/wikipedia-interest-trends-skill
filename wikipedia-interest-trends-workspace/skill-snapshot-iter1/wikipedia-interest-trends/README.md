# wikipedia-interest-trends: навичка для AI-агента

Навичка у форматі [Agent Skills](https://agentskills.io/specification), яка допомагає засновникам
B2C-продуктів вирішувати, **які теми розвивати і якими мовами запускатися**, за даними
переглядів Wikipedia (Wikimedia Analytics API).

Агент ставить запитання природною мовою, наприклад: *«Чи зростає інтерес до астрономії
в україномовній Wikipedia і наскільки цьому можна довіряти?»*. Навичка:

1. зіставляє тему зі статтями Wikipedia в усіх потрібних мовах (через Wikidata);
2. завантажує щоденні перегляди, кешує їх і нормалізує на загальний трафік мовного розділу;
3. рахує зростання з 95% інтервалами, оцінку довіри (HIGH/MEDIUM/LOW) з поясненнями,
   порівняння між мовами/темами та рейтинг перспективності;
4. будує графіки й односторінковий PDF-звіт (en/uk), а також перевіряє, що кожен відсоток у
   тексті агента збігається з розрахунками (*claim check*).

Вміст: `SKILL.md` (інструкції для агента), `scripts/` (код), `references/` (методологія, вибір
статей), `tests/` (офлайн-тести), `evals/` (тестові запити).

## Швидкий старт

Потрібні лише Python ≥ 3.9 та інтернет. Перший запуск сам створює ізольоване середовище
з закріпленими версіями (`requirements.txt`: numpy, matplotlib, reportlab):

```bash
python3 scripts/wt.py check                     # середовище + доступ до API
python3 scripts/wt.py selftest                  # 27 офлайн-тестів
python3 scripts/wt.py resolve "astronomy" --langs uk
python3 scripts/wt.py analyze --topic "Астрономія=Q333|Q318|Q525|Q634" --langs uk --months 36 --report-lang uk
python3 scripts/wt.py report wikitrends-output/<папка>
```

Змінні середовища: `WIKITRENDS_HOME` (де лежать venv і кеш, типово `~/.cache/wikitrends`),
`WIKITRENDS_CONTACT` (email або URL для User-Agent; Wikimedia просить вказувати контакт),
`WIKITRENDS_NO_VENV=1` (запускати поточним інтерпретатором, якщо залежності вже встановлено).

## Команди

| Команда | Що робить |
|---|---|
| `resolve "тема" … --langs pl,cs` | Wikidata QID і назви статей у кожній мові; якщо статті немає, показує результати пошуку в цьому розділі |
| `related uk:Астрономія` | тематичні «сусіди» статті (взаємні посилання) з переглядами за 60 днів і QID; для пошуку підтем |
| `analyze --topic "Назва=Q1\|Q2" --langs …` | завантаження, метрики, довіра, порівняння, рейтинг, графіки, `summary.md`, `analysis.json`, `data.csv`, чернетка `narrative.md` |
| `report <папка>` | односторінковий PDF з `narrative.md` + claim check |
| `check`, `cache info\|clear`, `selftest` | діагностика |

## Архітектура

```
SKILL.md ── агент: формулює питання → обирає статті → запускає CLI → інтерпретує → пише narrative.md
scripts/wt.py            лаунчер (stdlib): venv з pinned-залежностями, кросплатформний, з блокуванням
scripts/wikitrends/
  net.py        HTTP: User-Agent з контактом, ≤3 паралельних запитів, спільний між процесами
                ліміт швидкості (SQLite sliding window), Retry-After для 429, повтори 5xx
  cache.py      SQLite: завершені місяці кешуються назавжди, метадані з TTL
  wiki.py       Wikidata (пошук, sitelinks), MediaWiki (нормалізація назв, redirects, пошук,
                сусідні статті), країни читачів
  pageviews.py  щоденні ряди per-article/aggregate; докачує лише відсутні місяці
  stats.py      сплески, блоковий бутстреп, Theil-Sen + Mann-Kendall, зсуви рівня з перевіркою
                сезонності, правила довіри, перцентильні ранги
  analysis.py   оркестрація: кошики статей, redirects-auto, метрики, порівняння, рейтинг, попередження
  charts.py     PNG-графіки (без другої осі, кольори закріплені за рядом)
  text.py       summary для агента, чернетка narrative (en/uk), парсер і claim check
  report.py     PDF (reportlab + DejaVu Sans з matplotlib: латиниця й кирилиця), завжди 1 сторінка
  i18n.py       підписи en/uk; нова мова = нова колонка
```

### Ключові рішення і чому
- **Код робить усю роботу з даними, агент лише судження.** Дешева модель (Haiku) не пише
  власний код для API й статистики, тож менше помилок і токенів. Вивід CLI компактний і
  структурований, зі згенерованою чернеткою звіту, яку агенту достатньо відредагувати.
- **Відносне зростання** (частка теми в усіх переглядах мовного розділу) як головний сигнал.
  У 2025 році багато розділів втратили 10–25% «людського» трафіку через ШІ-пошук і
  перекласифікацію ботів, тож сирі перегляди вводять в оману.
- **Порівняння повних років** (останні 12 міс. проти попередніх 12) прибирає сезонність:
  шкільні теми влітку, дієти в січні.
- **Довіра як набір перевірок**, а не одне p-значення: інтервал, узгодженість по місяцях,
  залежність від сплесків, обсяг, домінування однієї статті, зсуви рівня, відомі збої даних
  (оновлення бот-детекції Wikimedia у травні–червні 2025). Кожна оцінка має пояснення.
- **Перевірка висновків**: `report` зіставляє всі відсотки в тексті з розрахованими метриками.
- **Ефективність повторних запитів**: кеш на рівні місяців (минулі дані незмінні), тож додати
  мову чи змінити ваги означає лише кілька нових запитів. Ліміт швидкості спільний для всіх
  процесів, тому паралельні агенти не отримують бан.
- **Мінімум залежностей** (без pandas/scipy): швидке й відтворюване встановлення.

## Перевірка якості
- `python3 scripts/wt.py selftest`: юніт-тести статистики й парсингу та **наскрізний офлайн-тест**
  (фейковий Wikimedia API: зростаючий ряд, перейменована стаття, відсутня стаття → PDF).
- `evals/evals.json`: три реалістичні запити з завдання. Прогін на **Claude Haiku 4.5** з
  навичкою і без неї (базовий рівень) описано в [результатах оцінювання](#результати-оцінювання-на-haiku).

## Обмеження
- Перегляди показують цікавість, а не готовність платити, тож потрібен другий сигнал.
- Мова ≠ країна; частина країн відсутня в даних Wikimedia про географію (захист читачів).
- Стаття є лише проксі теми; результат залежить від вибору кошика (агент його називає).
- Невиявлені боти можливі; дуже малі обсяги (< 20 переглядів/день) шумні.

## Як розвивати навичку далі

Розвивати варто ітеративно, як і першу версію: **спершу нові eval-запити, що ламають поточну
версію → зміна → прогін з навичкою і без → порівняння**. Орієнтовні кроки за зростанням
складності:

1. **Ширше покриття тем (зараз: ручні кошики 1–7 статей).**
   - Автоматичне формування кошиків із графа Wikidata (SPARQL: subclass of / part of /
     main subject), категорій і графа посилань; кластеризація за embeddings назв і описів.
   - Матриця покриття «тема × мова», щоб знаходити прогалини контенту масово.
   - Режим «discovery»: ендпоінт `top` (1000 найпопулярніших статей за день/місяць) для пошуку
     тем, що ростуть, без заздалегідь заданого списку.
2. **Більші обсяги даних (зараз: API, ~150 запитів/хв).**
   - Сотні й тисячі статей: перейти з per-article API на щомісячні дампи
     `pageview_complete` (dumps.wikimedia.org) і DuckDB/Parquet замість SQLite. Один дамп дає
     всі статті всіх мов без лімітів.
   - Фонові відновлювані завдання завантаження з прогресом; інкрементальне оновлення раз на місяць.
   - Попередньо агреговані «кошики» та зберігання лише місячних рядів для довгої історії (2015+).
3. **Сильніша статистика.**
   - STL-декомпозиція сезонності та прогноз з інтервалами (ETS) для горизонту 6–12 міс.
   - Детекція точок зміни (PELT) замість одного найбільшого зсуву; кращий бот-фільтр
     (аномалії співвідношення desktop/mobile, `automated`-частка).
   - Ієрархічні моделі між мовами (partial pooling) для малих розділів; поправка на множинні
     порівняння (FDR), коли рангуються десятки тем.
   - Розбивка за доступом (`mobile-app`/`mobile-web`/`desktop`) як сигнал мобільної аудиторії.
4. **Тріангуляція.** Конектори до Google Trends, ключових слів магазинів застосунків, Reddit;
   метрика `unique devices` Wikimedia для розміру аудиторії; зведена оцінка «попиту» з вагами.
5. **Продуктові сценарії.**
   - Збережені «дослідження» (YAML-специфікація тем/мов/ваг) для відтворюваних повторів і
     щомісячного моніторингу з алертом, якщо тренд змінився.
   - Інтерактивний HTML-дашборд; багатосторінковий deep-dive; більше мов звіту (таблиця `i18n.py`).
6. **Оцінювання як запобіжник регресій.** 20+ eval-запитів (уточнення після першої відповіді,
   неіснуючі теми, неоднозначні назви, дуже малі розділи), записані відповіді API як фікстури
   (VCR), оптимізація опису навички для тригерингу, контроль вартості й латентності на Haiku.
